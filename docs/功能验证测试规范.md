# 功能验证测试规范

本文档规定《星穹骇客（Star Hacker）》的统一验证流程。它说明“如何证明改动正确”，不重复玩法规则；预期行为与数值从 `docs/游戏机制与玩法内容.md` 和对应模块文档取得。

## 1. 项目基线

| 项目 | 当前值 |
| --- | --- |
| Godot 项目格式 | 4.7 |
| 验证引擎 | Godot 4.7.1 stable mono |
| 主场景 | `res://scenes/ui/main_menu.tscn` |
| 渲染模式 | GL Compatibility |
| 默认视口 | 1280×720 |
| 自动化基础 | Godot 无头导入、临时 `SceneTree` 脚本与人工验收；暂未引入正式测试框架 |

当前 WSL 环境使用以下控制台程序：

```text
/mnt/e/Godot/Godot_v4.7.1-stable_mono_win64/Godot_v4.7.1-stable_mono_win64/Godot_v4.7.1-stable_mono_win64_console.exe
```

安装位置变化时可替换路径，但验证引擎不得低于项目资源格式要求。

## 2. 验证原则

### 2.1 五级门禁

1. 需求追踪：每条需求都有实现位置、验证方式与精确预期。
2. 静态一致性：差异、注册入口、命名、注释、资源引用和文档一致。
3. Godot 解析：全部脚本、场景和资源能由目标引擎导入。
4. 无头行为：公式、边界、反向条件、状态、信号和存档可重复断言。
5. 人工集成：真实输入、物理、布局、动画、拖拽与跨场景流程符合预期。

后一级不能掩盖前一级失败。改动范围允许跳过不适用的门禁，但测试报告必须说明理由。例如纯文档整理通常只需需求追踪、静态一致性与引用核对，不要求启动游戏。

### 2.2 可追溯性

每项验证至少记录：

- 验证对象与关联需求。
- 存档、模式、装备、随机种子和环境等前置条件。
- 可复现步骤。
- 包含数值、事件次数或可见结果的预期。
- 实际结果与通过、失败或受限结论。
- 命令退出码、完成标记、日志、截图或录屏等证据。

只写“测试通过”不构成完整记录。

### 2.3 自动化与人工边界

- 资源默认值、公式、兼容资格、概率配置、状态机、信号次数和序列化优先自动化。
- 输入手感、真实物理组合、窗口布局、文本截断、颜色、动画、音效和拖拽必须人工验收。
- 关键规则应同时验证数据结果和玩家结果；不要只断言内部方法，也不要用一次目测代替确定性公式测试。

## 3. 测试准备

### 3.1 阅读与差异检查

1. 阅读机制总表中的对应章节。
2. 阅读模块文档；没有专用文档时阅读 `game_framework.md`。
3. 使用 `git status --short` 区分任务改动与用户原有改动。
4. 使用 `git diff -- <路径>` 检查实际范围。
5. 使用 `rg` 定位受影响的属性、资源 ID、路径、序列化字段和 UI 消费者。

### 3.2 需求验证矩阵

| 编号 | 规则或数值 | 实现位置 | 自动验证 | 人工验证 | 通过标准 |
| --- | --- | --- | --- | --- | --- |
| R1 | 正常路径 | 脚本或资源 | 直接断言 | 对应操作 | 精确结果 |
| R2 | 最小、最大、零或空值 | 数据或服务 | 边界断言 | 必要时操作 | 不越界、不误生效 |
| R3 | 不兼容或失败路径 | 校验入口 | 反向断言 | 灰显或拒绝 | 不消费、不写入 |
| R4 | 保存与恢复 | 序列化服务 | 当前结构往返 | 重启游戏 | 状态一致 |

涉及概率时同时验证配置和固定种子抽样；涉及时序时验证边界前、边界值和边界后；涉及资格时必须验证至少一个不应生效的目标。

### 3.3 用户数据安全

AutoLoad 会访问：

- `user://character_unlocks.json`
- `user://global_inventory.json`
- `user://shop_state.json`
- `user://stock_market_state.json`
- `user://mining_farm_state.json`
- `user://input_bindings.cfg`
- `user://ui_style_settings.cfg`
- `user://banner_notification_settings.cfg`
- `user://debug_settings.cfg`
- `user://save_delete_pending_v1.marker`

纯资源与纯组件测试不得调用保存接口。需要验证 AutoLoad、交易、锻造、存档往返或存档删除时，先确认实际用户目录并完整备份；优先使用独立测试账号、测试机、隔离项目名或引擎独立 `--user-data-dir`。训练场不会结算正式物品得失，但部分 UI 和全局服务仍可能写入存档，因此不属于完整沙箱。删除验证还必须清理 `.temp_import`、`.temp_delete` 与保护标记，禁止把临时测试档案留在日常用户目录。

库存服务专项约束：手动实例化的 `GlobalInventory` 不得拥有 `user://` 写入权限；自动验证必须断言非 `/root/GlobalInventory` 实例调用 `_save_inventory()` 后主存档内容与修改时间均保持不变。测试结束后不得遗留延迟调用、未释放实例或额外库存备份文件。

## 4. 标准流程

### 4.1 静态一致性

在项目根目录执行：

```bash
git status --short
git diff --check
git diff --stat
```

随后按范围检索：

```bash
rg -n "属性名|资源ID|资源路径" scripts data scenes docs
rg -n "SAVE_PATH|SAVE_VERSION|serialize|deserialize" scripts/game
```

检查以下事项：

- 新内容是否通过 `ContentCatalog` 进入所有声明的业务范围。
- 新属性是否进入公式、兼容、随机池、详情、筛选、序列化和聚合入口。
- 场景外部资源、脚本类名、稳定 ID 和 `load_steps` 是否有效。
- 新变量是否具有项目要求的长期维护注释。
- 对应模块文档与机制总表是否同步。
- 是否遗留冲突标记、临时脚本、日志、截图或意外修改。

纯文档改动还应检查标题层级、相对引用、术语、事实来源和重复权威定义。规划内容必须明确标注为未实现。

### 4.2 Godot 全量导入

```bash
GODOT_EXE="/mnt/e/Godot/Godot_v4.7.1-stable_mono_win64/Godot_v4.7.1-stable_mono_win64/Godot_v4.7.1-stable_mono_win64_console.exe"
"$GODOT_EXE" --headless --path . --import
```

也可使用：

```bash
"$GODOT_EXE" --headless --path . --editor --quit
```

通过条件：退出码为 `0`，且输出不包含 `ERROR`、`SCRIPT ERROR`、`Parse Error`、资源加载失败或无效路径。不能只看退出码，因为部分 Godot 错误不会稳定返回非零状态。

### 4.3 无头行为验证

Windows Godot 不能直接读取 WSL `/tmp`。临时脚本统一放在项目根目录并命名为：

```text
.tmp_verify_<feature>.gd
```

执行命令：

```bash
"$GODOT_EXE" --headless --path . --script .tmp_verify_<feature>.gd
```

最小模板：

```gdscript
extends SceneTree

## 本轮失败状态；默认 false，任意断言失败后变为 true，并决定最终退出码。
var _verification_failed: bool = false


func _init() -> void:
	await process_frame
	_run_verification()
	print("feature_verification_passed" if not _verification_failed else "feature_verification_failed")
	quit(1 if _verification_failed else 0)


func _run_verification() -> void:
	## 被测资源模板；把占位路径替换为任务中的真实资源，先校验加载结果再创建副本。
	var source_resource: Resource = load("<resource_path>")
	_check(source_resource != null, "资源必须成功加载")
	if source_resource == null:
		return
	## 被测资源副本；深拷贝可避免修改加载缓存并污染同类测试。
	var tested_resource: Resource = source_resource.duplicate(true)
	_check(tested_resource != null, "资源必须成功复制")


func _check(condition: bool, failure_message: String) -> void:
	if condition:
		return
	_verification_failed = true
	push_error("验证失败：%s" % failure_message)
```

通过条件：进程自行结束、退出码为 `0`、包含唯一完成标记，且没有脚本错误或断言失败。测试完成后删除临时脚本。

## 5. 自动测试设计

### 5.1 数据与公式

- 加载资源并确认类型、默认字段、稳定 ID 和有效值。
- 修改 `duplicate(true)` 副本，确认模板不变。
- 覆盖基础值、单次增减、多次累计、正负抵消与最终上下限。
- 分别验证“是否持有属性”和“属性数值”；显式持有但数值为零不等于不存在。
- UI 展示的实际变化必须用同一有效值公式复算。

### 5.2 概率与随机

- 配置层直接断言权重、概率、区间端点及权重总和。
- 抽样层固定 `RandomNumberGenerator.seed`，验证结果范围、去重、目标类型与必要的宽容差分布。
- 不得用一次随机结果证明概率，也不得用抽样替代配置常量断言。
- 多类别掉落需验证类别独立性、空池回退、倍率为零、正常倍率和概率上限。

### 5.3 状态、信号与批处理

- 验证调用前、第一次调用、中间锁定、边界前后和完成状态。
- 一次操作只结算规定次数的能量、耐久、星穹、材料和信号。
- 闭包信号计数使用可变数组或字典，避免局部整数写回问题。
- 需要 `get_tree()` 或物理世界的节点先加入场景树并等待必要帧。
- 可蓄力武器与技能必须模拟“按下、松开均发生在下一物理帧前”的同帧单击：按下请求只能消费 1 次，释放上下文必须为 `charge_seconds=0`、`charge_ratio=0`，基础攻击或行为必须成功且不得重复结算能量、耐久、冷却或信号。
- 分帧批处理覆盖最小量、最大量、不同批大小、重复操作、完成与失败恢复；全批次只持久化和最终刷新一次。
- 空闲处理优化需要同时验证“初始关闭、业务开始后启用、状态结束后关闭”三个阶段；关闭处理不得冻结冷却、持续时间、长按进度、结算信号或重新激活入口。
- 高频物理查询优化必须验证复用的 Shape2D、RID 排除表和距离平方缓存属于单个实例，不被其他弹体或攻击组件共享污染；穿透后排除表只追加实际目标且不会重复命中。
- UI 降频刷新必须验证数据所有者仍按原精度推进，显示在配置间隔内更新；输入按下与松开、生命能量信号和操作资格变化不得被批量刷新延迟。
- 装备套装缓存必须覆盖初始化、穿戴、卸下、受击损坏、强化和修复已装备防具后的即时失效；同一装备快照内重复移动、增伤、减伤、宝箱与击杀查询不得重新统计四个防具槽。未激活附近掉落物效果时不得扫描 `item_drops`，激活后仍需验证 300 像素边界、移动方向点积与多个掉落物不重复叠加。
- 修复信号测试需要分别覆盖已装备与未装备物品：已装备物品成功恢复耐久后必须恰好触发装备重算并恢复普通属性与套装门槛，仓库或背包物品修复只更新库存和持久化状态，不得触发战斗装备刷新。
- 库存性能验证至少覆盖隐藏背包、隐藏仓库、隐藏锻造面板与可见长列表：隐藏状态收到信号后只能标记待刷新，不得排队卡片重建；可见状态同一帧多个关联信号最多执行 1 次完整重建。
- 怪物图鉴自动验证需要覆盖空 ID 拒绝、首次 `register_monster_encounter(monster_id)` 解锁、同一 ID 重复登记不重复写入，以及 `is_monster_discovered()` 对不同 ID 的隔离；涉及写盘的集成测试必须使用隔离用户目录。
- 长列表卡片复用验证需要记录移动前后的控件实例 ID：容器内移动后全部未增删物品保持原实例，跨容器移动后仅来源移出项和目标新增项允许变化；所有复用卡片的真实来源下标、数量、悬停状态与拖拽数据必须同步到最新库存。
- 正式战斗拾取与丢弃需要断言普通库存变化不立即排队完整存档，成功、失败和正常退出结算能够保存最终状态；物资撤离点的安全送回路径必须独立断言仍可强制即时保存。
- 物资撤离面板需要同时验证左侧两个远程槽、一个近战槽和右侧头部、躯干、腿部、脚部四个固定槽均可见；对每一种已装备物品验证报价、灰显资格、送回后从原槽移除、进入仓库与即时保存，空槽必须不可操作。
- 可堆叠资源丢弃需要覆盖数量 1、2 与 10：每次操作只生成 1 个地面节点，节点数量与请求一致，拾取后节点移除且背包增加相同数量；地图剩余掉落物总价值必须按单件价值乘节点数量计算。
- 背包容量验证需要覆盖第 49、50、51 组边界、满 50 组时补充已有未满堆叠、仓库转入、拾取、卸下装备和部分移动；失败操作必须保持来源数量、目标数量与所有权完全不变。
- 仓库展开背包后的标题需要断言显示真实 `当前组数/50`，并验证切换分类、搜索、强化属性筛选和排序后数字不随可见条目数量变化。
- 仓库与共享背包强化石卡片需要分别断言第三行只包含属性方向、第四行只包含整组价值；修复包和普通物品不得因该规则产生空白第四行。
- 锻造主槽与五个牺牲槽分别放入普通及特化强化石，断言第三行显示按利弊着色的属性方向且不包含“资源 · 强化石”。
- 局内与局外背包的强化石品质筛选分别覆盖全部、初级、中级、高级、极品、特化，并与关键词和属性方向组合验证；切换一级分类后必须恢复全部品质。
- 武器与装备固定价值验证分别连续使用初级、中级、高级、极品、特化强化石，断言满耐久价值依次累计 `5/10/25/50/100`，负面词条与多词条不改变单颗加值；序列化往返后品质计数与价值必须保持一致。
- 锻造费用需要分别使用相同基础价值、相同强化石品质记录和相同锻造材料的武器与装备，在满耐久、半耐久、零耐久状态下断言主物品费用价值、费用倍率与纯强化费用完全一致；加入耐久牺牲品时只允许实际恢复耐久产生的基础费用随耐久缺口变化。
- 当前库存读档需要构造 1、10、11 与 99 件数量，断言合法数量原样恢复，超过 10 的异常数量直接限制到 10，不拆组、不转仓库，也不触发迁移回写。
- 武器与四部位装备的强化次数都需要覆盖 0、19、20 次与第 21 次：悬停、锻造来源卡牌和锻造预览显示必须一致，剩余 1 次时允许一颗并拒绝两颗，达到上限后仍允许纯耐久修复，最终执行不得扣除超额强化石或星穹。
- 二手生成验证必须固定随机种子并分别覆盖怪物、宝箱与商店武器装备：判定概率常量为 30%，命中样本的历史强化次数位于 1 至 20，次数 `n` 的配置权重为 `21 - n`、总权重为 210 且相邻次数严格递减（1 次 `20/210≈9.52%`、20 次 `1/210≈0.48%`）；耐久消耗整数位于 1% 至 99%，每颗历史强化石品质来自正式 `38.8%/29.1%/19.4%/9.7%/3%` 分布，名称统一带“【二手】”，序列化往返后状态不丢失。

### 5.4 物理

最小物理场景至少验证碰撞层与掩码、目标与墙体顺序、高速扫掠、重复命中去重、穿透与阻挡、最大距离和回收。至少执行一次低帧率或较大 `delta` 场景，防止正常帧率掩盖漏判。

散射、连击等组合攻击先测试纯数据生成，再测试真实弹体和时序；覆盖单个、奇偶数量、零偏移、边界值和一次攻击的统一成本。

### 5.5 序列化与当前结构恢复

- 验证序列化字段完整和当前结构往返一致。
- 验证缺失可选字段、非法记录和过期资源 ID 不会破坏其他有效记录。
- 验证历史版本号不会触发默认资产补发、商店重建、强化公式转换、股市进度缩放、图鉴补账或项目目录复制。
- 存档删除必须在隔离用户目录中构造全部 9 个白名单文件与至少 1 个非白名单文件：正确短语确认后白名单活动文件和两类内部临时文件全部消失，非白名单文件保持不变；错误短语、缺字、多字与附加空格都不得提交删除。
- 删除保护标记必须覆盖“本次删除后退出阶段重新写入旧活动文件”的情形：下一次启动时 `SaveArchiveService` 在其他业务 AutoLoad 读档前再次清理，随后移除标记并按首次启动默认值初始化。
- 自动测试优先断言内存快照；只有文件 I/O、离线时间或跨进程恢复需要隔离存档集成测试。

### 5.6 模式扩展与风险合约

- 直接断言规则表包含需求声明的十九个稳定词条 ID、玩家显示名、效果倍率与掉落加成；不得只检查 UI 文本数量。
- 固定随机种子至少抽取 100 批候选，每批必须恰好四项且效果类别互不重复；配置入口还需覆盖未知 ID、重复项、同类多档、超过四项、空合约和超频不兼容。
- 选择面板需要覆盖未启用扩展可确认、启用风险合约后自动生成四项、未选词条禁用确认、选择一项恢复确认、刷新替换四项并清空选择、返回不提交。
- 组合倍率至少覆盖一组怪物属性风险和一组功能风险，精确断言人口、生命、移速、攻击力、耐久、视野、背包、小地图、正式撤离点数量与加算后的掉落倍率。
- 背包容量分别断言 `38 / 25 / 13` 组；额外覆盖入场前已有物品超过新上限时不删除、已有未满堆叠仍可补充、新增物品组被拒绝、结算后恢复 `50`。
- 真实 `GameWorld` 冒烟必须从 `SessionState` 写入配置，确认右上角小地图、玩家与装备组件、全局库存、怪物属性和四类掉落概率均收到同一规则结果。
- 真实 `GameWorld` 冒烟还需验证无撤离数量词条时存活 120 秒生成 3 个正式撤离点，点位两两优先满足 4000 像素间距；`extraction_points_one` 汇总效果覆盖为 1 个出口。
- 真实 `CombatHud` 必须验证暂停主页左栏按钮文案、`1280×720` 下的 `(20, 338)` 坐标与 `420×44` 尺寸；打开后断言规范化词条 ID、每项规则表奖励、加算总奖励、空合约 `+0%`、ESC 优先关闭，以及宽版设置页隐藏入口。
- 联机使用两份隔离用户目录验证房主配置、准备清空、客户端只读摘要、晚加入补发和最终开局权威；怪物效果只由主机结算，本地玩家限制在两端一致。

## 6. 人工验收

### 6.1 战斗与物理

- 在训练场记录测试前生命、能量、耐久、冷却和属性。
- 在空旷、墙边、最大距离、多个目标和资源不足条件下验证。
- 对每种可蓄力武器与技能分别验证极短单击、短按、满蓄三档；极短单击必须立即使用 `0 秒 / 0%` 基础效果，不能漏放、卡在蓄力状态或额外释放一次。
- 切换武器、装备、背包、暂停和恢复后再次检查状态。
- 确认输入锁定、视觉反馈、伤害次数和自动断言一致，控制台无新增错误。

### 6.2 UI 与库存

- 检查所有复用同一控件的页面，不只检查首次出现问题的页面。
- 验证文字、价格、耐久、方向、筛选、排序、点击、拖拽、灰显、失败与成功状态。
- 操作失败不得扣款、消费或移动所有权；成功后 UI、真实数据和存档一致。
- 长列表同时验证滚轮和可见滚动条拖动。等待布局完成后确认滚动条有像素宽度、存在可滚范围且设置值能够生效。
- 在目标分辨率和必要的窄窗口下检查文本截断、按钮溢出、弹窗尺寸和控件重叠。
- 在单人骇入入口检查“骇入模式 → 模式扩展 → 战斗”和“模式扩展返回 → 骇入模式”两条路径；风险合约四项词条、独立奖励、总奖励、刷新和至少一项门槛必须清晰可操作。联机面板同时检查第三个“模式扩展”规则行、房主可编辑与客户端只读状态。
- 在主菜单验证“金融 ▲”与“统计 ▲”：点击后分别只展开“炒股、矿场、保险、银行”或“图鉴、生涯”，分类互斥且箭头翻为“▼”；再次点击、按 ESC 或打开任一子入口后恢复“▲”。从金融四项打开并关闭面板时焦点返回金融分类，从图鉴或生涯关闭时焦点返回统计分类。
- 在主菜单设置与暂停设置分别检查“UI风格设置”下拉框：选项顺序必须为“黑蓝科技风、黑白简约风”。切换黑白简约风后，普通窗口、输入框、下拉菜单、滚动条、通用进度条和所有 `HSlider` 的轨道、进度、滑块立即切为黑白色板；角色选择页的生命与能量预览条应为灰阶，战斗 HUD 的生命、能量、武器耐久、地图图标和标记、物品品质、涨跌/收益/警告及红色危险按钮保持原色。标准物品卡片与紧凑 HUD 槽位的背景、边框应切为灰阶，但耐久和绿色合法目标保持原色。确认不创建灰度 `ShaderMaterial`、不改变任一控件原有 `Material`，并且战斗世界画面保持原色。
- 打开“图鉴 / 怪物”确认基础内容和每个扩展包各自独立分组，未遇到条目只显示“？？？”。进入含未解锁怪物的战斗并等待其获得玩家目标后，重新打开图鉴必须立即显示名称、说明、近远程类型和基础数值；重启、怪物死亡、休眠后再次物化均保持已解锁状态，重复遇到不得新增重复条目或重复写盘。

### 6.3 跨场景与存档

- 验证主菜单、主大厅、角色选择、正式战斗、训练场及各自返回路径；大厅需额外覆盖实体碰撞、最近目标 F 交互、面板输入锁定和菜单双向切换。
- 验证成功撤离、死亡与主动逃跑的不同结算。
- 验证仓库、背包、装备、商店、灰市、股市和矿场之间的资产边界。
- 完全退出并重启，确认当前版本存档可恢复；旧结构存档不属于验收范围。
- 在主菜单设置与暂停设置分别检查“删除存档”危险按钮、480×240 输入弹窗、错误输入禁用状态和正确短语可用状态；确认删除后进程自动重启，角色、物品、货币、局外系统、按键、UI 风格与调试选项均与首次启动一致。

## 7. 按改动类型选择范围

| 改动类型 | 必做自动验证 | 必做人工验证 | 必查文档 |
| --- | --- | --- | --- |
| 纯文档 | 差异、引用、事实抽查、`git diff --check` | 不适用 | 导航与受影响文档 |
| 数据资源或默认数值 | 加载、字段、有效值、自动注册 | 详情与实际效果 | 机制总表、内容制作 |
| 战斗组件 | 状态、次数、时序、边界 | 训练场、墙体、多目标、切换 | 机制总表、框架 |
| 强化与随机 | 兼容、公式、权重、固定种子 | 锻造、结果、详情 | 机制总表、框架 |
| 库存、商店或锻造 | 原子操作、数量、价值、往返 | 点击、拖拽、交易、重启 | 机制总表、框架 |
| 存档结构调整 | 当前版本往返、缺失与非法字段、删除白名单与启动保护 | 备份存档重启、删除后首次启动状态 | 对应模块 |
| UI | 格式化、查询、组件实例化 | 分辨率、输入、滚动、弹窗 | UI 规范、对应模块 |
| 敌人 AI | 状态、记忆、路径、模拟生命周期 | 遮挡、绕障、脱战、多怪 | AI、机制总表 |
| 模式扩展 | 规则表、候选去重、兼容、组合倍率、真实世界接线、联机最终权威 | 单人/联机窗口、刷新、地图、视野、背包与耐久体感 | 模式扩展、联机、机制总表、UI 规范 |
| 股市或矿场 | 公式、时间推进、交易、往返 | 完整流程与跨重启 | 对应模块、机制总表 |

跨类型改动取各范围并集。回归范围由共享组件和数据流决定，不由修改文件数量决定。

## 8. 失败、清理与完成标准

失败时保留首个根因、命令、退出码和复现条件。修复后重跑失败项、该级门禁及相邻回归。测试脚本生命周期、路径或环境错误应先修复测试基础，不得据此修改正常产品逻辑。

完成前确认：

- 需求矩阵无遗漏。
- `git diff --check` 通过。
- 所有适用门禁通过，跳过项有理由。
- 文档、资源、场景与脚本事实一致。
- 用户数据未污染或已恢复。
- `.tmp_verify_*.gd`、日志和截图等临时文件已删除。
- 最终工作区只包含任务改动和用户原有改动。
