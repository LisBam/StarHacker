# 功能验证测试规范

本文档是《崩坏：量子骇袭》功能开发完成后的统一验证规范，适用于数据资源、战斗组件、武器装备、强化锻造、库存商店、存档迁移、UI、敌人 AI、股市、矿场及后续新增模块。所有同类功能应按本文档建立测试范围、执行验证、记录结果，并在项目结构、Godot 版本、测试入口或风险模型变化时持续更新本文档。

本文档固化的是“如何证明功能正确”，不替代具体玩法设计。玩法规则与数值以 `docs/游戏机制与玩法内容.md` 为准，模块职责与数据流以对应模块文档和 `docs/game_framework.md` 为准。

## 1. 文档基线

- 当前适配项目版本：Godot `4.6` 项目格式，验证引擎为 Godot `4.6.3 stable mono`。
- 当前主场景：`res://scenes/ui/main_menu.tscn`。
- 当前渲染模式：`GL Compatibility`，默认视口为 `1280×720`。
- 当前自动化基础：项目暂未引入 GUT 等正式测试框架，主要使用 Godot 无头导入、临时 `SceneTree` 验证脚本和训练场人工验收。
- 当前维护日期：`2026-07-12`。
- 当前 Windows 控制台程序：`E:\Godot\Godot_v4.6.3-stable_mono_win64\Godot_v4.6.3-stable_mono_win64\Godot_v4.6.3-stable_mono_win64_console.exe`。
- WSL 中对应程序路径：`/mnt/e/Godot/Godot_v4.6.3-stable_mono_win64/Godot_v4.6.3-stable_mono_win64/Godot_v4.6.3-stable_mono_win64_console.exe`。

若引擎路径因本机安装位置变化，可替换命令中的程序路径；不得擅自降低引擎版本验证，因为低版本可能无法正确解析项目的 `4.6` 资源格式和 API。

## 2. 核心原则

### 2.1 五级验证门禁

每次功能代码改动必须依次通过以下五级门禁：

1. 需求与文档追踪：确认每条需求均有实现位置、验证方法和预期结果。
2. 静态一致性：检查差异、资源注册、属性命名、注释、文档和临时文件。
3. Godot 全量解析：导入全部资源并解析脚本、场景和资源引用。
4. 无头行为断言：直接验证数据、边界、状态变化、事件次数和时序。
5. 人工集成验收：在训练场或对应正式界面验证操作手感、UI、物理交互和跨模块结果。

任一级失败都必须回到对应实现修复。后续级别“看起来正常”不能替代前一级失败，例如画面能运行不能证明资源注册完整，单次随机结果正确不能证明概率权重正确。

### 2.2 验证结论必须可追溯

每项验证必须明确记录：

- 验证对象：具体脚本、场景、资源或功能入口。
- 前置条件：存档状态、装备、模式、随机种子、输入与环境。
- 操作步骤：可由其他开发者重复执行的顺序。
- 预期结果：包含具体数值、事件次数、状态变化或可见表现。
- 实际结果：通过、失败或受限，并记录关键输出。
- 证据：命令退出码、完成标记、日志、截图或录屏。

只记录“测试通过”不构成完整测试记录。

### 2.3 自动化与人工测试边界

- 数值公式、资源默认值、兼容资格、存档结构、概率配置、状态机和事件次数优先自动化。
- 碰撞体实际交互、输入手感、动画、窗口布局、文本截断、颜色、拖拽、音效和多场景流程必须人工验收。
- 自动化测试负责快速、稳定地发现确定性错误；人工测试负责发现呈现层、真实物理环境和组合交互问题。
- 同一关键规则应尽量同时拥有数据层断言和实际玩法验收，避免只测试实现细节而遗漏玩家结果。

## 3. 测试开始前的准备

### 3.1 阅读顺序

1. 阅读 `docs/游戏机制与玩法内容.md` 中对应功能的规则与数值。
2. 阅读对应模块文档；没有独立模块文档时阅读 `docs/game_framework.md`。
3. 查看 `git status --short`，识别当前任务改动、用户原有改动和未跟踪文件。
4. 使用 `git diff -- <相关路径>` 检查实际变更范围。
5. 使用 `rg` 定位所有属性名、资源 ID、资源路径、序列化字段和 UI 展示入口。

### 3.2 需求验证矩阵

编码完成后先建立需求验证矩阵。每条需求至少对应一个直接验证项；高风险需求应覆盖正常、边界和反向场景。

| 需求编号 | 规则或数值 | 实现位置 | 自动验证 | 人工验证 | 通过标准 |
| --- | --- | --- | --- | --- | --- |
| R1 | 功能正常路径 | 脚本/资源 | 具体断言 | 具体操作 | 精确结果 |
| R2 | 最小值、零值或空值 | 脚本/资源 | 边界断言 | 必要时操作 | 不越界、不误生效 |
| R3 | 不兼容目标 | 数据/服务 | 反向断言 | 灰显或拒绝 | 不消费、不写入 |
| R4 | 存档恢复 | 序列化服务 | 往返断言 | 重启游戏 | 状态完全一致 |

不得只验证新增成功路径。涉及资格判断时必须额外验证“不应生效”的目标；涉及数值上下限时必须验证最低值、最高值与越界输入；涉及概率时必须验证配置权重与抽样结果；涉及存档时必须验证保存、读取和旧版本迁移。

### 3.3 用户数据安全

项目 AutoLoad 会访问以下 `user://` 文件：

- `global_inventory.json`：仓库、背包、装备、金币和部分局外资产。
- `shop_state.json`：商店库存、刷新状态和灰市。
- `stock_market_state.json`：股市行情与证券币状态。
- `mining_farm_state.json`：矿场资产与收益状态。
- `input_bindings.cfg`：自定义按键。
- `debug_settings.cfg`：调试选项。

执行测试时遵守以下规则：

- 纯资源和纯组件测试使用 `--script` 启动临时 `SceneTree`，不要主动访问 AutoLoad，也不要调用任何保存接口。
- 需要验证 AutoLoad、购买、锻造、存档或迁移时，必须先在 Godot 编辑器中通过“打开用户数据文件夹”确认真实目录并完整备份。
- 破坏性存档测试优先使用独立系统账号、独立测试机或专用测试项目名，不得直接覆盖日常游玩存档。
- 测试结束后恢复备份，并重新进入主菜单核对仓库、金币、商店、股市和矿场状态。
- 训练场用于战斗验证时不会结算物品得失或怪物掉落，但 UI 操作和部分全局服务仍可能写入 `user://`；不能把“训练场”理解为完整存档沙箱。

## 4. 标准验证流程

### 4.1 第一级：需求与文档追踪

执行步骤：

1. 把需求拆成独立、可验证的行为和数值。
2. 为每项需求定位数据源、执行组件、持久化入口和 UI 展示入口。
3. 确认对应模块文档和《游戏机制与玩法内容》已经同步。
4. 检查文档记录的默认值、概率、时间、费用、下限和公式是否与代码、场景覆盖值、`.tres` 一致。

通过标准：

- 每条需求均能在验证矩阵中定位。
- 不存在仅写代码但没有验证方案的需求。
- 不存在代码、场景和文档对同一数值给出不同结论。

### 4.2 第二级：静态一致性检查

在项目根目录执行：

```bash
git status --short
git diff --check
git diff --stat
```

随后按改动类型执行精确检索，例如：

```bash
rg -n "属性名|资源ID|资源路径" scripts data scenes docs
rg -n "SAVE_PATH|serialize|deserialize|版本字段" scripts/game
```

检查内容：

- 新资源是否加入所有必要入口：资源路径表、掉落池、商店池、首次存档、开发者发放、场景依赖和存档恢复。
- 新属性是否加入规则目录、标签、方向、公式分类、随机池、详情、筛选、结果弹窗、序列化与聚合组件。
- 场景 `load_steps` 与外部资源声明是否完整。
- 变量是否有长期维护注释，导出变量是否说明用途、范围、默认值和运行时影响。
- 是否意外修改用户已有文件、变量名或原注释。
- 是否遗留 `.tmp_verify_*.gd`、测试日志、截图或临时资源。
- `git diff --check` 是否存在新增空白错误。

通过标准：

- `git diff --check` 退出码为 `0`。
- 没有当前改动引入的尾随空格、冲突标记或临时文件。
- 所有注册入口和文档入口均已覆盖。
- 对工作区原有换行警告只可记录，不能误称为本次错误，也不能擅自改写无关文件消除警告。

### 4.3 第三级：Godot 全量资源导入与解析

推荐先定义程序变量，所有路径必须加双引号：

```bash
GODOT_EXE="/mnt/e/Godot/Godot_v4.6.3-stable_mono_win64/Godot_v4.6.3-stable_mono_win64/Godot_v4.6.3-stable_mono_win64_console.exe"
"$GODOT_EXE" --headless --path . --import
```

也可使用编辑器启动并在首轮完成后退出：

```bash
"$GODOT_EXE" --headless --path . --editor --quit
```

验证目的：

- 导入新增或变化的 `.tres`、`.tscn` 和其他资源。
- 解析项目脚本及全局类名。
- 校验场景外部资源引用、脚本类名和资源格式。
- 发现编辑器缓存尚未刷新时被普通文本检查遗漏的问题。

通过标准：

- 进程退出码为 `0`。
- 输出不包含 `ERROR`、`SCRIPT ERROR`、`Parse Error`、`Failed loading resource` 或无效 UID/路径。
- 新增资源完成导入，场景可重新加载。
- 不允许仅以进程退出码判断；必须同时搜索错误文本，因为部分 Godot 脚本错误不会稳定转换为非零退出码。

### 4.4 第四级：无头行为验证

#### 4.4.1 临时脚本位置

Windows Godot 可执行文件不能直接访问 WSL 的 `/tmp`。临时验证脚本必须放在项目根目录，例如：

```text
.tmp_verify_<功能名>.gd
```

运行时使用项目相对路径：

```bash
"$GODOT_EXE" --headless --path . --script .tmp_verify_<功能名>.gd
```

测试完成后必须删除临时脚本，并用 `git status --short` 确认没有残留。

#### 4.4.2 标准脚本模板

以下模板适用于资源、组件和时序测试。测试应输出唯一完成标记，并显式使用退出码结束进程。

```gdscript
extends SceneTree

## 本轮是否发现失败；默认 false，任意校验失败后置为 true，并在结束时返回非零退出码。
var _verification_failed: bool = false


func _init() -> void:
	# 等待首个场景树帧；需要把 Node 加入树、访问 get_tree() 或创建物理对象时必须等待。
	await process_frame
	_run_verification()
	# 完成标记；日志中缺失该文本表示脚本未完整执行到结尾，不能判定通过。
	print("feature_verification_passed" if not _verification_failed else "feature_verification_failed")
	# 显式退出；避免弹体、计时器或其他活动节点让无头进程永久运行。
	quit(1 if _verification_failed else 0)


func _run_verification() -> void:
	# 被测资源；必须 duplicate(true)，避免测试修改已加载模板或污染同类测试。
	var tested_resource: Resource = load("res://data/example.tres").duplicate(true)
	_check(tested_resource != null, "资源必须成功加载")
	if tested_resource == null:
		return
	# 此处按需求矩阵执行正常、边界与反向校验。


func _check(condition: bool, failure_message: String) -> void:
	if condition:
		return
	_verification_failed = true
	push_error("验证失败：%s" % failure_message)
```

通过标准：

- 命令退出码为 `0`。
- 输出包含本次测试约定的唯一 `*_verification_passed` 标记。
- 输出不包含 `ERROR`、`SCRIPT ERROR` 或断言失败。
- 进程在预期时间内自行退出，不依赖人工终止。

#### 4.4.3 数据与资源测试

至少覆盖：

- 新资源可以加载且类型正确。
- 默认字段与机制文档完全一致。
- 有效值接口返回预期结果。
- 修改副本不会改变模板资源。
- 零值、空值、最小值、最大值和异常输入经过夹取后结果正确。
- 兼容目标返回 `true`，不兼容目标返回 `false`。
- 不兼容操作不会写入数据、消费物品或改变价值。

对于“是否具有属性”与“属性数值”分离的设计，必须分别验证存在性和数值。数值为 `0` 不等于没有属性，例如基础穿透为 `0` 的武器仍可显式持有穿透能力；不得只使用 `value > 0` 判定属性是否存在。

#### 4.4.4 公式与概率测试

公式测试必须验证：

- 基础值。
- 单次增强和单次削弱。
- 多次累计与正负抵消。
- 最终下限和上限。
- UI 使用的实际变化值与最终值一致。

概率测试分两层：

1. 配置层：直接断言权重、概率常量和品质区间端点。例如稀有属性权重必须精确为常规属性的 `0.2`。
2. 抽样层：使用固定 `RandomNumberGenerator.seed` 重复抽取，验证所有结果位于合法区间、无重复词条、目标类型正确，并在需要时使用宽容差检查长期分布。

不得使用一次随机结果证明概率正确。抽样统计不能替代配置层断言，因为样本即使落入预期范围也可能掩盖错误权重；配置层断言也不能替代抽样，因为抽样可发现池构建、去重和方向选择错误。

#### 4.4.5 组件、信号与时序测试

至少验证：

- 操作开始前状态。
- 第一次调用的返回值和事件次数。
- 中间状态是否阻止重复操作。
- 时间推进到边界前、边界时和边界后的状态。
- 完成后是否进入正确冷却或空闲状态。
- 一次玩家操作是否只结算规定次数的能量、耐久、金币或材料。

测试信号次数时，GDScript 闭包对局部整数的赋值不会可靠回写外层局部变量。使用可变数组或字典保存计数：

```gdscript
# 信号计数容器；使用可变数组保证闭包内修改对外层校验可见。
var fired_count: Array[int] = [0]
attack_component.fired.connect(func(_projectile: Node2D) -> void: fired_count[0] += 1)
```

需要实例化 `Node` 的测试必须先把节点加入场景树；组件内部调用 `get_tree()`、`get_world_2d()` 或解析父节点路径时，未入树节点会产生空引用。弹体、计时器和 `_process()` 活动节点可能让测试进程保持运行，因此测试结尾必须显式 `quit()`，必要时先 `queue_free()` 或 `free()` 清理节点。

属性面板或聚合快照必须分别断言 `total`、`base` 和 `equipment`，并用独立公式复算 `total = base + equipment`。生命需额外验证当前值与总上限，比例属性需明确显示语义：移速比例先换算实际速度点数，视野以 100% 为基础，闪避率以 0% 为基础。装备穿脱、损坏和角色切换后都要重新断言，防止刷新顺序导致装备加成丢失或重复累计。

多段攻击与冷却 UI 需要覆盖首段、中间段、末段完成瞬间和完成后一帧。若设计为连击期间冷却满值，必须断言首发后立即为 100%、中间段不减少、末段结束后仍为 100%，随后才随 `delta` 下降；不能只验证最终可再次攻击的时间。

#### 4.4.6 批量异步操作测试

批量生成、导入或发放为避免卡顿而分帧执行时，至少验证：

- 最小数量 1、配置最大数量和非法零值的处理。
- 批大小为 1、默认值和大于总量时都能结束。
- 非最后批次确实让出场景树帧，最后批次不产生无意义等待。
- 生成期间重复操作被禁用或串行化，完成与失败后控件都恢复可用。
- 全部批次只触发一次持久化和一次最终 UI 刷新，禁止每批重建长列表。
- 返回数量、真实新增单位数和用户反馈文本一致；堆叠合并不能让“记录组数”冒充“物品单位数”。

涉及 AutoLoad 存档的批量测试优先验证纯生成器、源代码契约和内存记录；只有在独立测试用户目录或完整备份后才能调用真实保存入口。人工验收最大数量时记录操作开始至界面恢复可交互的时间，并观察鼠标、窗口和进度反馈是否持续响应。

#### 4.4.7 物理与碰撞测试

纯方法调用不能完整证明物理行为。涉及弹体、穿透、击退、视线、墙体、拾取范围或导航时，应建立最小测试场景或使用训练场验证：

- 碰撞层与掩码正确。
- 目标和墙体的先后顺序正确。
- 高速物体的扫掠碰撞没有漏判。
- 同一目标不会因 Area 与射线重复命中。
- 可穿透目标与不可穿透环境遵守不同规则。
- 达到最大距离、寿命或次数后对象被正确回收。

物理测试至少执行一次低帧率或较大 `delta` 场景，防止只在正常帧率下通过。

散射武器应先对纯角度生成接口执行固定种子测试，再进入物理场景验证弹体。至少覆盖散射数量 1、2、奇数、偶数、较大值和偏移为 0：

- 正偏移时主弹必须落在 `[-偏移 × 中心比例, +偏移 × 中心比例]`，且多轮固定种子样本不能全部为 0；全部弹体角度均落在 `[-偏移, +偏移]`。
- 奇数总弹数除主弹外左右数量相同；其余弹体必须保持在分配侧，层级随机后不得跨越瞄准线或相邻层级。
- 偶数总弹数左右数量只能相差 1，连续多轮应能观察到多出弹体位于两侧，禁止长期固定偏向。
- 每颗弹体都必须实际消费随机值；同一固定种子连续多轮的主弹和侧弹角度应出现变化，同时整体仍保持主弹靠近瞄准、侧弹分散的结构。
- 偏移为 0 时允许全部弹道重合，但弹体数量不得减少；普通非散射武器仍应保持单弹完整区间随机偏移，不得被散射分层算法改变。

#### 4.4.8 序列化与迁移测试

存档相关功能至少验证：

- 新对象序列化后包含全部必要字段。
- `序列化 → 反序列化` 往返后数值、类型、数量、强化、耐久和元数据一致。
- 旧版本缺失字段使用预期默认值。
- 旧公式、旧耐久上限或旧资源 ID 按迁移规则转换。
- 非法、空或过期记录安全拒绝，不破坏其他有效记录。
- 保存失败时内存状态和错误处理符合设计。

自动化优先直接调用快照接口验证内存字典，不要为了验证一个序列化字段就覆盖真实 `user://` 文件。只有验证文件读写、离线时间或跨进程恢复时才执行隔离存档集成测试。

### 4.5 第五级：人工集成验收

#### 4.5.1 训练场战斗功能

通用步骤：

1. 备份用户数据并启动项目主菜单。
2. 进入训练场，装备明确的被测资源。
3. 记录测试前生命、能量、耐久、冷却和属性详情。
4. 在空旷区域验证基础行为。
5. 在墙边、多个目标重叠、最大射程和能量不足条件下验证边界。
6. 切换武器、打开背包、暂停和恢复后再次验证状态。
7. 离开训练场，确认没有发生正式模式物品得失结算。

战斗功能通过标准：

- 画面表现、伤害次数、资源消耗和无头断言一致。
- 输入锁定、暂停、切换装备和 UI 冷却显示不破坏状态机。
- 墙体、目标、射程、偏移、击退和回收表现符合机制文档。
- 控制台没有新增运行时错误。

#### 4.5.2 UI、库存、商店和锻造

至少检查：

- 主菜单、战斗背包、仓库、商店、灰市、锻造、结算和物资撤离中的相关卡片。
- 名称、类型、数值、正负方向、价格、耐久和详情格式。
- 搜索、分类、属性筛选和排序。
- 点击、拖拽、数量选择、灰显、禁用和替换流程。
- 操作失败时不扣金币、不消费材料、不移动所有权。
- 操作成功后 UI、真实库存和存档同时更新。
- 关闭并重新进入界面后状态仍正确。
- 长列表必须制造超过可视区域的条目，分别用滚轮和拖动滚动条滑块到达首尾；常驻滚动条在内容不足时可禁用滑块，但轨道仍应可见。
- 自动化不能只断言 `vertical_scroll_mode == SCROLL_MODE_SHOW_ALWAYS`。必须等待容器至少两帧完成布局，再断言垂直滚动条实际宽度大于 0、`max_value > page`，并把 `value` 设置为最大可滚动值确认其大于 0；否则主题把滚动条压成 0 像素时会产生“逻辑通过、玩家看不见”的假阳性。
- 带页签的共享面板必须验证默认页、逐项切换、切回状态、数据刷新和两种宿主上下文；不能只在主菜单或只在战斗中验收。

#### 4.5.3 存档与跨场景流程

至少检查：

- 主菜单进入战斗再返回主菜单。
- 角色系统入口、确认与返回必须独立验证：确认只修改当前角色并返回主菜单，返回不修改角色，骇入和训练场直接进入战斗且使用最后确认角色。
- 保存后完全退出游戏并重新启动。
- 正式模式成功撤离、死亡和主动逃跑的不同结算。
- 仓库、背包、装备栏、商店、灰市、股市和矿场之间的所有权边界。
- 旧存档升级后不重复发放默认物品、不丢失原有资产。

## 6. 回归测试标准

功能直接测试通过后，至少回归以下相邻链路：

- 数据资源变化：回归加载、详情、价值、筛选、存档恢复和所有生成池。
- 武器变化：回归能量、耐久、后坐力、冷却 HUD、弹体和装备切换。
- 装备变化：回归穿脱、损坏、属性聚合、生命比例、移动、相机和能量恢复。
- 强化变化：回归石头生成、堆叠签名、锻造兼容、价值、结果弹窗和旧存档。
- 商店变化：回归自动刷新、手动刷新、二手状态、购买、存档和灰市。
- UI 变化：回归所有复用同一控件的界面，不得只检查首次发现问题的页面。
- 存档变化：回归首次存档、当前版本、至少一个旧版本和损坏记录。

回归范围由共享组件和数据流决定，而不是由修改文件数量决定。单文件修改可能影响所有复用者。

## 7. 失败处理与复测

出现失败时按以下顺序处理：

1. 保存完整命令、退出码和首个根因错误；后续连锁错误仅作辅助。
2. 判断失败属于测试环境、测试脚本还是产品代码。
3. 先用最小复现确认根因，再修改实现或测试。
4. 修复后重跑失败项。
5. 重跑该级全部验证，避免修复只覆盖单一断言。
6. 重跑后续门禁和相邻回归。
7. 在测试记录中保留失败原因和修复结论。

测试脚本自身失败不等于产品代码失败。例如节点未加入树导致 `get_tree()` 为空、Windows Godot 无法读取 WSL `/tmp`、闭包计数未回写或测试进程未显式退出，都属于测试基础设施错误。必须修复测试后重新验证，不能据此修改正常产品逻辑。

## 8. 常见避坑要点

### 8.1 路径与运行环境

- 项目路径和 Godot 路径包含空格时必须使用双引号。
- 在 shell 中检索 Markdown 内容时，不要把反引号直接写进双引号命令；反引号会触发命令替换，应改用单引号模式或移除反引号后检索关键字。
- Windows Godot 只能稳定访问 Windows 文件系统映射路径；不要把 `--script` 指向 WSL `/tmp`。
- 命令必须在包含 `project.godot` 的项目根目录执行，或显式传入正确 `--path`。
- 不要用与项目版本不一致的 Godot 可执行文件混跑导入缓存。

### 8.2 SceneTree 生命周期

- 在 `SceneTree._init()` 中立即测试节点树行为可能得到空 `get_tree()`；先 `await process_frame`。
- 调用组件前先 `root.add_child(component)`，需要父节点路径时显式配置测试父节点。
- 测试生成弹体、计时器或持续处理节点后必须显式 `quit()`。
- 测试超时后终止进程只是清理措施，不是通过结果；必须查清未退出原因并重跑。

### 8.3 数据资源

- 修改被测资源前使用 `duplicate(true)`，避免污染加载缓存和后续断言。
- 区分基础字段、强化累计值和最终有效值；战斗验证应读取最终有效值。
- 某些非强化配置字段不由 `get_effective_stat()` 返回，应按资源 API 设计直接读取，不能强行套用统一接口。
- 属性存在性不能一律由非零判断；使用显式持有标记或规则目录。

### 8.4 随机与时间

- 自动化随机测试必须设置固定种子。
- 区间测试必须覆盖全部品质、增强方向和削弱方向。
- 时间逻辑验证边界前、边界值和边界后，不要只推进一个很大的 `delta` 看最终状态。
- 大 `delta` 可能在同一帧同时完成等待并开始新冷却，断言应明确组件设计中的处理顺序。

### 8.5 日志与退出码

- Godot 输出完成标记但包含 `SCRIPT ERROR` 时仍判失败。
- Godot 退出码为 `0` 但缺少完成标记时仍判失败。
- 断言报错后活动节点可能让进程继续运行，因此标准脚本优先使用 `_check()` 聚合失败并显式 `quit(1)`。
- 已知无关警告必须记录来源；不得把所有警告忽略，也不得为消除无关警告修改任务外文件。

### 8.6 临时文件与工作区

- 临时脚本使用统一 `.tmp_verify_*.gd` 命名。
- 临时脚本、日志、截图只在测试期间存在，完成后删除。
- 最终执行 `git status --short`，不得遗留测试辅助文件。
- 工作区存在用户原有改动时必须保留，不得使用 `git reset --hard`、`git checkout --` 等破坏性清理命令。

## 9. 测试完成判定

只有同时满足以下条件才可声明功能验证完成：

- 需求验证矩阵全部有结果，无遗漏项。
- `git diff --check` 通过。
- Godot 全量导入与解析退出码为 `0`，无新增错误。
- 所有无头验证脚本退出码为 `0`，包含完成标记且无脚本错误。
- 必要的人工集成和边界场景通过。
- 相邻模块回归通过。
- 用户数据未被污染，或隔离测试数据已清理并恢复。
- 临时脚本和日志已删除。
- 关联模块文档与《游戏机制与玩法内容》已同步。
- 最终工作区只包含任务预期修改和用户原有改动。

## 11. 文档维护规则

以下变化发生时必须更新本文档：

- Godot 主版本、次版本或项目功能版本变化。
- 引入正式测试框架、CI、测试目录或统一测试运行脚本。
- 新增 AutoLoad、存档文件或用户数据隔离方式。
- 新增功能类别、共享组件或必须回归的跨模块链路。
- 发现新的测试环境陷阱、误判方式或遗漏类型。
- 现有命令、路径、完成标记或通过标准不再适用。

更新本文档时应从长期维护视角整合规则，避免仅追加一次性事故描述。新增避坑项必须说明触发条件、错误表现、正确处理和复测要求；删除旧规则前必须确认项目中已经不存在对应风险。
