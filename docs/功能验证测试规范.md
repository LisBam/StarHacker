# 功能验证测试规范

本文档规定《星穹骇客（Star Hacker）》的统一验证流程。它说明“如何证明改动正确”，不重复玩法规则；预期行为与数值从 `docs/游戏机制与玩法内容.md` 和对应模块文档取得。

## 1. 项目基线

| 项目 | 当前值 |
| --- | --- |
| Godot 项目格式 | 4.6 |
| 验证引擎 | Godot 4.6.3 stable mono |
| 主场景 | `res://scenes/ui/main_menu.tscn` |
| 渲染模式 | GL Compatibility |
| 默认视口 | 1280×720 |
| 自动化基础 | Godot 无头导入、临时 `SceneTree` 脚本与人工验收；暂未引入正式测试框架 |

当前 WSL 环境使用以下控制台程序：

```text
/mnt/e/Godot/Godot_v4.6.3-stable_mono_win64/Godot_v4.6.3-stable_mono_win64/Godot_v4.6.3-stable_mono_win64_console.exe
```

安装位置变化时可替换路径，但验证引擎不得低于项目资源格式要求。

## 2. 验证原则

### 2.1 五级门禁

1. 需求追踪：每条需求都有实现位置、验证方式与精确预期。
2. 静态一致性：差异、注册入口、命名、注释、资源引用和文档一致。
3. Godot 解析：全部脚本、场景和资源能由目标引擎导入。
4. 无头行为：公式、边界、反向条件、状态、信号和存档可重复断言。
5. 人工集成：真实输入、物理、布局、动画、拖拽与跨场景流程符合预期。

后一级不能掩盖前一级失败。改动范围允许跳过不适用的门禁，但测试报告必须说明理由。例如纯文档整理通常只需需求追踪、静态一致性与引用核对，不要求启动游戏。

### 2.2 可追溯性

每项验证至少记录：

- 验证对象与关联需求。
- 存档、模式、装备、随机种子和环境等前置条件。
- 可复现步骤。
- 包含数值、事件次数或可见结果的预期。
- 实际结果与通过、失败或受限结论。
- 命令退出码、完成标记、日志、截图或录屏等证据。

只写“测试通过”不构成完整记录。

### 2.3 自动化与人工边界

- 资源默认值、公式、兼容资格、概率配置、状态机、信号次数和序列化优先自动化。
- 输入手感、真实物理组合、窗口布局、文本截断、颜色、动画、音效和拖拽必须人工验收。
- 关键规则应同时验证数据结果和玩家结果；不要只断言内部方法，也不要用一次目测代替确定性公式测试。

## 3. 测试准备

### 3.1 阅读与差异检查

1. 阅读机制总表中的对应章节。
2. 阅读模块文档；没有专用文档时阅读 `game_framework.md`。
3. 使用 `git status --short` 区分任务改动与用户原有改动。
4. 使用 `git diff -- <路径>` 检查实际范围。
5. 使用 `rg` 定位受影响的属性、资源 ID、路径、序列化字段和 UI 消费者。

### 3.2 需求验证矩阵

| 编号 | 规则或数值 | 实现位置 | 自动验证 | 人工验证 | 通过标准 |
| --- | --- | --- | --- | --- | --- |
| R1 | 正常路径 | 脚本或资源 | 直接断言 | 对应操作 | 精确结果 |
| R2 | 最小、最大、零或空值 | 数据或服务 | 边界断言 | 必要时操作 | 不越界、不误生效 |
| R3 | 不兼容或失败路径 | 校验入口 | 反向断言 | 灰显或拒绝 | 不消费、不写入 |
| R4 | 保存与恢复 | 序列化服务 | 往返与迁移 | 重启游戏 | 状态一致 |

涉及概率时同时验证配置和固定种子抽样；涉及时序时验证边界前、边界值和边界后；涉及资格时必须验证至少一个不应生效的目标。

### 3.3 用户数据安全

AutoLoad 会访问：

- `user://character_unlocks.json`
- `user://global_inventory.json`
- `user://shop_state.json`
- `user://stock_market_state.json`
- `user://mining_farm_state.json`
- `user://input_bindings.cfg`
- `user://debug_settings.cfg`

纯资源与纯组件测试不得调用保存接口。需要验证 AutoLoad、交易、锻造或迁移时，先确认实际用户目录并完整备份；优先使用独立测试账号、测试机或隔离项目名。训练场不会结算正式物品得失，但部分 UI 和全局服务仍可能写入存档，因此不属于完整沙箱。

库存服务专项约束：手动实例化的 `GlobalInventory` 不得拥有 `user://` 写入权限；自动验证必须断言非 `/root/GlobalInventory` 实例调用 `_save_inventory()` 后主存档内容与修改时间均保持不变。测试结束后不得遗留延迟调用、未释放实例或额外库存备份文件。

## 4. 标准流程

### 4.1 静态一致性

在项目根目录执行：

```bash
git status --short
git diff --check
git diff --stat
```

随后按范围检索：

```bash
rg -n "属性名|资源ID|资源路径" scripts data scenes docs
rg -n "SAVE_PATH|SAVE_VERSION|serialize|deserialize" scripts/game
```

检查以下事项：

- 新内容是否通过 `ContentCatalog` 进入所有声明的业务范围。
- 新属性是否进入公式、兼容、随机池、详情、筛选、序列化和聚合入口。
- 场景外部资源、脚本类名、稳定 ID 和 `load_steps` 是否有效。
- 新变量是否具有项目要求的长期维护注释。
- 对应模块文档与机制总表是否同步。
- 是否遗留冲突标记、临时脚本、日志、截图或意外修改。

纯文档改动还应检查标题层级、相对引用、术语、事实来源和重复权威定义。规划内容必须明确标注为未实现。

### 4.2 Godot 全量导入

```bash
GODOT_EXE="/mnt/e/Godot/Godot_v4.6.3-stable_mono_win64/Godot_v4.6.3-stable_mono_win64/Godot_v4.6.3-stable_mono_win64_console.exe"
"$GODOT_EXE" --headless --path . --import
```

也可使用：

```bash
"$GODOT_EXE" --headless --path . --editor --quit
```

通过条件：退出码为 `0`，且输出不包含 `ERROR`、`SCRIPT ERROR`、`Parse Error`、资源加载失败或无效路径。不能只看退出码，因为部分 Godot 错误不会稳定返回非零状态。

### 4.3 无头行为验证

Windows Godot 不能直接读取 WSL `/tmp`。临时脚本统一放在项目根目录并命名为：

```text
.tmp_verify_<feature>.gd
```

执行命令：

```bash
"$GODOT_EXE" --headless --path . --script .tmp_verify_<feature>.gd
```

最小模板：

```gdscript
extends SceneTree

## 本轮失败状态；默认 false，任意断言失败后变为 true，并决定最终退出码。
var _verification_failed: bool = false


func _init() -> void:
	await process_frame
	_run_verification()
	print("feature_verification_passed" if not _verification_failed else "feature_verification_failed")
	quit(1 if _verification_failed else 0)


func _run_verification() -> void:
	## 被测资源模板；把占位路径替换为任务中的真实资源，先校验加载结果再创建副本。
	var source_resource: Resource = load("<resource_path>")
	_check(source_resource != null, "资源必须成功加载")
	if source_resource == null:
		return
	## 被测资源副本；深拷贝可避免修改加载缓存并污染同类测试。
	var tested_resource: Resource = source_resource.duplicate(true)
	_check(tested_resource != null, "资源必须成功复制")


func _check(condition: bool, failure_message: String) -> void:
	if condition:
		return
	_verification_failed = true
	push_error("验证失败：%s" % failure_message)
```

通过条件：进程自行结束、退出码为 `0`、包含唯一完成标记，且没有脚本错误或断言失败。测试完成后删除临时脚本。

## 5. 自动测试设计

### 5.1 数据与公式

- 加载资源并确认类型、默认字段、稳定 ID 和有效值。
- 修改 `duplicate(true)` 副本，确认模板不变。
- 覆盖基础值、单次增减、多次累计、正负抵消与最终上下限。
- 分别验证“是否持有属性”和“属性数值”；显式持有但数值为零不等于不存在。
- UI 展示的实际变化必须用同一有效值公式复算。

### 5.2 概率与随机

- 配置层直接断言权重、概率、区间端点及权重总和。
- 抽样层固定 `RandomNumberGenerator.seed`，验证结果范围、去重、目标类型与必要的宽容差分布。
- 不得用一次随机结果证明概率，也不得用抽样替代配置常量断言。
- 多类别掉落需验证类别独立性、空池回退、倍率为零、正常倍率和概率上限。

### 5.3 状态、信号与批处理

- 验证调用前、第一次调用、中间锁定、边界前后和完成状态。
- 一次操作只结算规定次数的能量、耐久、星穹、材料和信号。
- 闭包信号计数使用可变数组或字典，避免局部整数写回问题。
- 需要 `get_tree()` 或物理世界的节点先加入场景树并等待必要帧。
- 可蓄力武器与技能必须模拟“按下、松开均发生在下一物理帧前”的同帧单击：按下请求只能消费 1 次，释放上下文必须为 `charge_seconds=0`、`charge_ratio=0`，基础攻击或行为必须成功且不得重复结算能量、耐久、冷却或信号。
- 分帧批处理覆盖最小量、最大量、不同批大小、重复操作、完成与失败恢复；全批次只持久化和最终刷新一次。
- 库存性能验证至少覆盖隐藏背包、隐藏仓库、隐藏锻造面板与可见长列表：隐藏状态收到信号后只能标记待刷新，不得排队卡片重建；可见状态同一帧多个关联信号最多执行 1 次完整重建。
- 长列表卡片复用验证需要记录移动前后的控件实例 ID：容器内移动后全部未增删物品保持原实例，跨容器移动后仅来源移出项和目标新增项允许变化；所有复用卡片的真实来源下标、数量、悬停状态与拖拽数据必须同步到最新库存。
- 正式战斗拾取与丢弃需要断言普通库存变化不立即排队完整存档，成功、失败和正常退出结算能够保存最终状态；物资撤离点的安全送回路径必须独立断言仍可强制即时保存。
- 可堆叠资源丢弃需要覆盖数量 1、2 与 10：每次操作只生成 1 个地面节点，节点数量与请求一致，拾取后节点移除且背包增加相同数量；地图剩余掉落物总价值必须按单件价值乘节点数量计算。
- 背包容量验证需要覆盖第 49、50、51 组边界、满 50 组时补充已有未满堆叠、仓库转入、拾取、卸下装备和部分移动；失败操作必须保持来源数量、目标数量与所有权完全不变。
- 旧库存迁移需要构造 11、20 与 99 件堆叠，断言加载后全部拆为每组最多 10 件且总数量守恒；背包拆组超过 50 组时，溢出记录必须完整进入仓库。
- 武器强化次数需要覆盖 0、19、20 次与第 21 次：悬停和锻造预览显示必须一致，剩余 1 次时允许一颗并拒绝两颗，达到上限后仍允许纯耐久修复，最终执行不得扣除超额强化石或星穹。
- 二手生成验证必须固定随机种子并分别覆盖怪物、宝箱与商店武器装备：判定概率常量为 30%，命中样本的历史强化次数位于 1 至 20、耐久消耗整数位于 1% 至 99%，每颗历史强化石品质来自正式 `38.8%/29.1%/19.4%/9.7%/3%` 分布，名称统一带“【二手】”，序列化往返后状态不丢失。

### 5.4 物理

最小物理场景至少验证碰撞层与掩码、目标与墙体顺序、高速扫掠、重复命中去重、穿透与阻挡、最大距离和回收。至少执行一次低帧率或较大 `delta` 场景，防止正常帧率掩盖漏判。

散射、连击等组合攻击先测试纯数据生成，再测试真实弹体和时序；覆盖单个、奇偶数量、零偏移、边界值和一次攻击的统一成本。

### 5.5 序列化与迁移

- 验证序列化字段完整和往返一致。
- 验证仍受支持的每个旧版本、缺失字段、非法记录和过期资源 ID。
- 迁移后不得重复发放默认资产或破坏其他有效记录。
- 自动测试优先断言内存快照；只有文件 I/O、离线时间或跨进程恢复需要隔离存档集成测试。

## 6. 人工验收

### 6.1 战斗与物理

- 在训练场记录测试前生命、能量、耐久、冷却和属性。
- 在空旷、墙边、最大距离、多个目标和资源不足条件下验证。
- 对每种可蓄力武器与技能分别验证极短单击、短按、满蓄三档；极短单击必须立即使用 `0 秒 / 0%` 基础效果，不能漏放、卡在蓄力状态或额外释放一次。
- 切换武器、装备、背包、暂停和恢复后再次检查状态。
- 确认输入锁定、视觉反馈、伤害次数和自动断言一致，控制台无新增错误。

### 6.2 UI 与库存

- 检查所有复用同一控件的页面，不只检查首次出现问题的页面。
- 验证文字、价格、耐久、方向、筛选、排序、点击、拖拽、灰显、失败与成功状态。
- 操作失败不得扣款、消费或移动所有权；成功后 UI、真实数据和存档一致。
- 长列表同时验证滚轮和可见滚动条拖动。等待布局完成后确认滚动条有像素宽度、存在可滚范围且设置值能够生效。
- 在目标分辨率和必要的窄窗口下检查文本截断、按钮溢出、弹窗尺寸和控件重叠。

### 6.3 跨场景与存档

- 验证主菜单、角色选择、正式战斗、训练场和返回主菜单。
- 验证成功撤离、死亡与主动逃跑的不同结算。
- 验证仓库、背包、装备、商店、灰市、股市和矿场之间的资产边界。
- 完全退出并重启，确认当前存档与至少一个受支持旧存档均可恢复。

## 7. 按改动类型选择范围

| 改动类型 | 必做自动验证 | 必做人工验证 | 必查文档 |
| --- | --- | --- | --- |
| 纯文档 | 差异、引用、事实抽查、`git diff --check` | 不适用 | 导航与受影响文档 |
| 数据资源或默认数值 | 加载、字段、有效值、自动注册 | 详情与实际效果 | 机制总表、内容制作 |
| 战斗组件 | 状态、次数、时序、边界 | 训练场、墙体、多目标、切换 | 机制总表、框架 |
| 强化与随机 | 兼容、公式、权重、固定种子 | 锻造、结果、详情 | 机制总表、框架 |
| 库存、商店或锻造 | 原子操作、数量、价值、往返 | 点击、拖拽、交易、重启 | 机制总表、框架 |
| 存档迁移 | 版本输入、往返、缺失与非法字段 | 备份存档重启 | 对应模块 |
| UI | 格式化、查询、组件实例化 | 分辨率、输入、滚动、弹窗 | UI 规范、对应模块 |
| 敌人 AI | 状态、记忆、路径、模拟生命周期 | 遮挡、绕障、脱战、多怪 | AI、机制总表 |
| 股市或矿场 | 公式、时间推进、交易、往返 | 完整流程与跨重启 | 对应模块、机制总表 |

跨类型改动取各范围并集。回归范围由共享组件和数据流决定，不由修改文件数量决定。

## 8. 失败、清理与完成标准

失败时保留首个根因、命令、退出码和复现条件。修复后重跑失败项、该级门禁及相邻回归。测试脚本生命周期、路径或环境错误应先修复测试基础，不得据此修改正常产品逻辑。

完成前确认：

- 需求矩阵无遗漏。
- `git diff --check` 通过。
- 所有适用门禁通过，跳过项有理由。
- 文档、资源、场景与脚本事实一致。
- 用户数据未污染或已恢复。
- `.tmp_verify_*.gd`、日志和截图等临时文件已删除。
- 最终工作区只包含任务改动和用户原有改动。

## 10. 维护规则

引擎版本、测试框架、CI、AutoLoad、存档文件、验证命令或风险模型变化时同步更新本文档。新增规则必须描述适用条件和通过标准；一次性事故记录不进入长期规范，除非它揭示仍存在的通用风险。
